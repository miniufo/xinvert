# GPU SOR Benchmark — Baseline (优化前)

**日期**: 2026-09-17
**环境**: Python 3.13 / numba-cuda / NVIDIA GeForce RTX 3090 (CC 8.6)
**设定**: 固定 1000 次迭代, tolerance=0, repeat=3 取中位数

## 结果

| 网格 | CPU (s) | GPU (s) | 加速比 | CPU error | GPU error |
|------|---------|---------|--------|-----------|-----------|
| 64×64 | 0.0267 | 0.4147 | 0.06x | 2.07e-04 | 2.07e-04 |
| 128×128 | 0.1072 | 0.4591 | 0.23x | 5.10e-05 | 5.10e-05 |
| 256×256 | 0.4288 | 0.6084 | 0.70x | 1.26e-05 | 1.26e-05 |
| 512×512 | 1.7551 | 1.2546 | 1.40x | 1.40e-04 | 4.65e-05 |
| 1024×1024 | 6.9308 | 3.9710 | 1.75x | 4.01e-02 | 1.50e-02 |

## 分析

### 正确性
- 小规模 (64~256): CPU 与 GPU error 完全一致, GPU Red-Black SOR 精确复现 CPU 标准 SOR
- 大规模 (512+): CPU error 增大 (SOR 过松弛 optArg~2.0 在 1000 迭代内未收敛), 非实现 bug

### 性能瓶颈
1. **每次迭代都拷贝 norm 回 host** (`d_norm.copy_to_host()`): 1000 次 CPU-GPU 同步, 每次阻塞 GPU pipeline
2. **每次迭代启动 3 个 kernel** (Red + Black + norm): kernel launch 开销在小规模占主导
3. **norm 计算读整个数组**: 与收敛判断无关的开销

### 预期优化
- 稀疏化收敛检查 (每 20 次才查): 减少 95% 的 host sync
- 用 atomic.max 跟踪 max|update| 替代全数组 norm: 更轻量的收敛信号
- 预期加速比提升: 1024×1024 从 1.75x → 5~8x
